\chapter{Implementation and Evaluation}
\label{ch:implementation}

\section{Introduction}

This chapter covers the implementation of the IPDC offline-first digital one-stop service prototype and the results of its evaluation. The implementation turns the architecture described in Chapter~\ref{ch:analysis} into a working Progressive Web Application made up of over 100 TypeScript source files, three trained machine learning models, and a thorough offline-first data management layer. The evaluation then puts the prototype through its paces with technical testing of offline functionality, performance measurement, cross-platform compatibility checks, and a usability assessment.

\section{Development Environment and Tools}

\subsection{Development Setup}

The development environment was built around Visual Studio Code as the primary IDE, Node.js (v18+) as the JavaScript runtime, React 19.2.1 \citep{React2024} as the frontend framework, and the Vite development server for hot module replacement at \texttt{localhost:5173}. Firebase emulators were used during development to test authentication and Firestore operations locally, avoiding unnecessary consumption of cloud quotas. The AI model backend was developed separately in a Python environment using FastAPI, with models available at \texttt{localhost:8000}.

\subsection{Build and Deployment Configuration}

The Vite build configuration uses manual chunk splitting to improve caching behavior. Three vendor chunks are carved out: \texttt{vendor} (React and ReactDOM), \texttt{mui} (Material-UI components), and \texttt{firebase} (Firebase SDKs). Keeping these separate means that updates to application code do not force browsers to re-download cached vendor libraries---a particularly worthwhile optimization where connectivity is limited.

The vite-plugin-pwa takes care of generating the service worker and web app manifest automatically from the configuration in \texttt{vite.config.ts}. The deployed platform can be accessed at the following URLs:

\begin{itemize}
  \item \textbf{Frontend Application:} \url{https://ipdc-oss-platform.vercel.app/} --- deployed on Vercel, providing HTTPS, global CDN distribution, and automatic SSL certificate management.
  \item \textbf{AI Backend API:} \url{https://ipdc-oss-platform.onrender.com/api/docs} --- deployed on Render, hosting the FastAPI server with the three trained ML models. The interactive API documentation (Swagger UI) is available at this URL, while model endpoints are served under the \texttt{/api/v1/} prefix (e.g., \texttt{/api/v1/classify-service}, \texttt{/api/v1/predict-maintenance}, \texttt{/api/v1/recommend-parks}).
\end{itemize}

\section{Key Feature Implementation}

\subsection{Offline-First Architecture Implementation}

The offline-first architecture is brought to life through three cooperating subsystems: Firebase Firestore's transparent cache, the Dexie.js local database, and a custom synchronization service.

\textbf{Firebase Offline Persistence} is switched on in the Firebase configuration module (\texttt{src/config/firebase.ts}) with two function calls during initialization:

\begin{lstlisting}[language=Java, caption={Firebase Offline Persistence Configuration}, label={lst:firebase-config}]
initializeFirestore(app, {
  localCache: persistentLocalCache({
    tabManager: persistentMultipleTabManager()
  })
});
\end{lstlisting}

This tells Firestore to maintain a persistent local cache of all documents the user has accessed, keeping the cache intact across browser sessions and coordinating access when multiple tabs are open. When the network is unavailable, reads are served from this cache, and writes are internally queued by Firestore for synchronization later.

\textbf{Dexie.js Local Database} extends Firestore's cache with explicit offline data management. The database schema, defined in \texttt{src/db/schema.ts}, sets up two indexed tables:

\begin{lstlisting}[language=Java, caption={Dexie.js Database Schema}, label={lst:dexie-schema}]
const db = new Dexie('IPDCDatabase');
db.version(1).stores({
  serviceRequests:
    'id, tenantId, status, priority, serviceType, createdAt',
  syncQueue:
    '++id, type, collection, status, createdAt'
});
\end{lstlisting}

\textbf{The Sync Service} (\texttt{src/services/offline/syncService.ts}) picks up sync queue items once connectivity is detected. It walks through pending items, converts local JavaScript \texttt{Date} objects to Firestore \texttt{Timestamp} objects, writes to the appropriate Firestore collection, and marks each queue item with an updated status. A built-in retry mechanism handles transient failures so that queued data is never lost.

\subsection{Authentication with Offline Fallback}

The authentication system puts into practice the dual-mode design outlined in Chapter~\ref{ch:analysis}. The \texttt{AuthContext} (\texttt{src/contexts/AuthContext.tsx}) wraps the entire application and keeps track of authentication state. When the user signs in online, credentials are verified through Firebase Auth and then cached locally:

\begin{lstlisting}[language=Java, caption={Credential Caching After Online Authentication}, label={lst:auth-cache}]
// After successful Firebase Auth sign-in:
await cacheCredentials(email, password);
await cacheAuthState({
  uid: user.uid,
  email: user.email,
  displayName: user.displayName,
  role: userData.role
});
\end{lstlisting}

If the sign-in attempt fails because of a network error, the context seamlessly falls back to offline verification:

\begin{lstlisting}[language=Java, caption={Offline Authentication Fallback}, label={lst:auth-offline}]
// Network error detected during sign-in:
const isValid = await verifyOfflineCredentials(email, password);
if (isValid) {
  const cachedUser = await getCachedAuthState();
  // Grant access using cached user profile
}
\end{lstlisting}

This means that any user who has previously logged in while online can continue using the platform during connectivity outages. Figure~\ref{fig:auth-interfaces} shows the sign-in and tenant registration interfaces.

\subsection{Service Request Management}

Service request management forms the backbone of the platform. The \texttt{CreateRequestForm} component (\texttt{src/components/tenant/}) relies on React Hook Form for state management and Zod for schema validation. Requests can be categorized across multiple service types (maintenance, IT support, security, cleaning, waste management, and others), assigned one of four priority levels, given free-text descriptions, and accompanied by file attachments uploaded through the \texttt{FileUpload} component to Firebase Storage.

Each request follows a defined status progression: \texttt{pending} $\rightarrow$ \texttt{approved} $\rightarrow$ \texttt{in-progress} $\rightarrow$ \texttt{completed}. Administrators also have the option to \texttt{reject} a request along with a reason. Every status transition triggers a notification and updates the request record in Firestore (or in the local queue when offline). \subsection{AI Model Integration}

Three machine learning models are connected to the platform through a FastAPI backend. The frontend AI service module (\texttt{src/services/aiService.ts}) exposes typed interfaces for each model endpoint, complete with error handling and timeout management.

\textbf{Model 1 --- Service Classifier:} Trained on labeled service request data, this model sorts incoming requests into eleven service categories and assigns priority levels. Because the classification endpoint returns a confidence score, the interface can present predictions as suggestions that users are free to accept or override.

\textbf{Model 2 --- Predictive Maintenance:} This model takes in asset attributes and produces a failure probability, risk level (low/medium/high), estimated days until failure, and a recommended maintenance action. By identifying assets that are approaching failure thresholds, it helps inform maintenance scheduling decisions.

\textbf{Model 3 --- Park Recommendation:} Built to help prospective tenants choose a suitable industrial park, this model evaluates a tenant profile against park characteristics using a weighted scoring algorithm. Five dimensions---industry alignment (30\%), capacity and availability (25\%), infrastructure match (20\%), cost efficiency (15\%), and location preference (10\%)---feed into ranked recommendations that come with detailed justifications.

All three models are designed with graceful degradation: if the API cannot be reached, the interface simply disables AI features without disrupting the core service request and management workflows. \subsection{Model 2: Predictive Maintenance System}

\subsubsection{Architecture}

The predictive maintenance system combines two algorithms in a dual-algorithm ensemble: Random Forest for classification and Gradient Boosting for regression. Fourteen engineered features are derived from raw asset attributes, including age in days, days since last maintenance, cumulative maintenance count, operating hours, historical failure count, sensor readings (temperature, vibration level), and a composite condition score computed as:

\begin{equation}
\text{Condition Score} = \frac{\text{age\_months}}{120} \times 30 + \frac{\text{days\_since\_maint}}{365} \times 30 + \text{failures} \times 10 + \frac{\text{hours}}{20000} \times 10
\label{eq:condition-score}
\end{equation}

Categorical features (asset category, status, condition level) are encoded with LabelEncoder, and all features are normalized using StandardScaler.

\subsection{Model 3: Park Recommendation System}

\subsubsection{Architecture}

The park recommendation model uses LightGBM's LambdaRank algorithm, a learning-to-rank approach that directly optimizes Normalized Discounted Cumulative Gain (NDCG). Each of the 800 tenant profiles is paired with all 13 Ethiopian industrial parks, producing 10,400 ranking instances. Match scores (0--100) are mapped to five relevance grades: 0 (poor, 0--20), 1 (fair, 20--40), 2 (good, 40--60), 3 (very good, 60--80), and 4 (excellent, 80--100).

Eleven features describe each tenant-park pair: three categorical features (industry sector, park identifier, preferred region) encoded with LabelEncoder, and eight numerical features (investment capital, employee count, land needed, power requirement, water requirement, export orientation, minimum budget, maximum budget).

\section{Prototype Demonstration}

\subsection{Tenant Workflow}

A typical tenant workflow unfolds as follows: the tenant logs in (whether online or offline), views their dashboard showing active requests and token balance, creates a new service request by picking a category and priority and attaching relevant documents, monitors the request status as it moves through approval and fulfillment, and files a complaint if the completed service falls short of expectations.

\subsection{Admin Workflow}

The administrator workflow revolves around processing incoming requests: reviewing submissions, approving or rejecting them with feedback, assigning approved requests to operations personnel, creating announcements for park-wide communication, managing tenant accounts and token allocations, and resolving complaints with the appropriate actions.

\subsection{Offline Operation Demonstration}

The offline workflow showcases the platform's core value proposition. With network connectivity turned off (simulated through browser DevTools or physical disconnection): the user logs in using cached credentials; browses previously loaded data from the Firestore cache; submits a new service request, which gets saved to IndexedDB and queued for sync; and the \texttt{StatusBar} displays ``Offline'' status along with a ``1 pending sync'' indicator. When connectivity comes back: the sync service automatically processes the queue; the request shows up in Firestore and becomes visible to administrators; and the \texttt{StatusBar} updates to ``Online'' with ``0 pending sync''. \subsubsection{Task Scenarios}

Each participant completed four structured task scenarios on the prototype before filling out the SUS questionnaire:

\begin{enumerate}

\item \textbf{View an announcement} --- find the announcements section and read the most recent park notice.

\subsubsection{SUS Score Calculation}

The System Usability Scale consists of ten Likert-scale items alternating between positive and negative phrasing \citep{Brooke1996}. For each participant, the contribution of each item is calculated as: (score $- 1$) for odd-numbered positive items and (5 $-$ score) for even-numbered negative items. The contributions are summed and multiplied by 2.5 to produce an individual score on a 0--100 scale. The mean across the nine participants is:

\[
\bar{S} = \frac{77.5 + 72.5 + 75.0 + 70.0 + 75.0 + 77.5 + 72.5 + 72.5 + 77.5}{9} = \frac{670.5}{9} \approx \mathbf{74.5}
\]

Following the adjective rating scale established by \citet{Bangor2009}, a score of 74.5 falls in the \textbf{``Good''} range. It exceeds the widely cited industry average of 68, indicating that stakeholders perceive the platform as genuinely usable despite the inherent complexity of a multi-role, offline-capable system.

\subsubsection{Qualitative Feedback}

Post-task open-ended feedback was collected from participants. Positive themes included:

\begin{itemize}
\item \textbf{Clarity of offline status indicator.} Several participants noted that the real-time online/offline status bar gave them confidence when connectivity was unreliable: \textit{``This is itself best for the future --- you can see exactly when it is working offline''} (P6, Adama SEZ).
\item \textbf{Straightforward request submission.} Tenant representatives appreciated the step-by-step request form: \textit{``Digital platform to have serving and communicating in one window''} (P8, Kombolcha SEZ).
\item \textbf{Token balance visibility.} Management staff found the token dashboard useful for tracking service fee obligations without contacting the finance department.
\end{itemize}

Areas identified for improvement included:

\begin{itemize}
\item \textbf{Amharic language support} (noted by six of nine participants as a priority for wider roll-out among non-English-speaking staff).
\item \textbf{Confirmation dialogs before token deductions} (requested by three tenant participants who wanted an explicit ``Are you sure?'' prompt before submitting requests that deduct tokens).
\item \textbf{Richer push notifications} (two management staff participants wanted mobile notifications for request status changes rather than relying on checking the dashboard).
\end{itemize}

These findings are consistent with the requirements gathered from the 49-respondent questionnaire (Section~\ref{sec:data-collection}): both data sources highlight Amharic localisation and proactive notification as the most impactful near-term improvements.

\section{Chapter Summary}

This chapter documented the implementation and evaluation of the IPDC platform prototype, comprising roughly 105 source files with dual-layer offline storage, dual-mode authentication, a tiered digital service token system, three AI models, and Workbox-powered PWA configuration. All three AI models show strong performance on synthetic evaluation data: the XGBoost service classifier achieves 100\% category accuracy, the predictive maintenance ensemble reaches $R^{2} = 0.9989$, and the LambdaRank park recommender achieves NDCG@3 of 0.9572; these results are best interpreted as an architectural baseline, with deployment on real IPDC operational data providing the definitive validation. Technical evaluation confirms all nine offline scenarios pass, Lighthouse performance scores (89/87/96/92) meet targets, full compatibility holds across Chrome and Opera on both desktop and mobile, a usability evaluation with nine real IPDC stakeholders on 10 February 2026 yields a SUS mean score of 74.5 (``Good''), and all seven of Hevner's DSR guidelines are satisfied. The next chapter pulls these findings together into design principles and maps out directions for future work.
